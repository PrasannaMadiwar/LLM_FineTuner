# LLM Fine-Tuner

Browser-based fine-tuning workspace with a Next.js frontend, FastAPI API, Celery worker, Supabase PostgreSQL, hosted Redis, and RunPod GPU orchestration.

## Architecture

```text
Next.js web application
  -> FastAPI API
    -> Supabase PostgreSQL (llm_finetuner schema)
    -> Hosted Redis (cache, Celery broker, and result backend)
    -> Celery worker
      -> RunPod GPU runtime agent
```

The web application, API, and worker are Docker services. PostgreSQL and Redis are external managed services; Docker Compose does not start local database or cache containers.

## Deployment

Render deployment is configured in [`render.yaml`](render.yaml). It creates a public API service, a public web service, and a Celery background worker.

See [`RENDER_DEPLOY.md`](RENDER_DEPLOY.md) for the required environment variables, Render Blueprint steps, worker-plan requirement, and upload-storage limitation.

## Local GPU Demo

The GPU layer is provider-agnostic: the training pipeline only talks to the `GPUProvider`
interface. `GPU_PROVIDER=runpod` rents cloud GPUs; `GPU_PROVIDER=local` runs the same GPU agent
image as a container on this machine's NVIDIA GPU. Both use the same job lifecycle
(create instance → upload dataset → train → collect artifacts → terminate).

Requirements: an NVIDIA GPU with 8 GB+ VRAM, a recent NVIDIA driver, and Docker Desktop with the
WSL 2 backend (GPU support is built in).

```powershell
docker build -t llm-finetuner-gpu-agent:local gpu-agent   # one-time, several GB
docker compose up --build
```

Open http://localhost:13000, register, and on the Fine-Tune page either click **Use built-in demo
dataset** (527 bundled Q&A rows, works offline, trains in about 2.5 minutes) or pick a Hugging Face
dataset, click **Normalize Dataset**, and fine-tune **Qwen2.5 1.5B Instruct**. The built-in dataset
goes through the same normalize → validate → train pipeline as a remote one; it is generated by
`apps/api/app/infrastructure/datasets/demo_data/generate_demo_dataset.py`. `DATASET_MAX_ROWS` (default 2000 in Docker Compose) keeps the demo run
to minutes. The first run downloads the model into the `llm-finetuner-hf-cache` volume; later runs
reuse it. Trained adapters stay in the `llm-finetuner-gpu-workspace` volume under
`artifacts/<training-id>/`.

Verified on an RTX 5050 Laptop GPU (8 GB): 2,000 alpaca rows, 1 epoch (250 steps) of 4-bit LoRA
on Qwen2.5 1.5B takes about 6 minutes end to end (first training step after ~1 minute, then about
one step per second), shows live loss/ETA on the job page, and produces a 74 MB adapter. Run one job
before presenting: the very first job also downloads the model (~3 GB), which is then cached.

The local provider runs one GPU container at a time and needs the Docker socket mounted into the
API and worker containers. That is only for a local demo: never mount the Docker socket on a
publicly reachable server.

Troubleshooting:

- *"The local GPU is already in use by …"* — a previous job's container is still running. Wait for
  it, or remove it with `docker rm -f <name>`.
- *"GPU agent image … was not found"* — build it with the `docker build` command above.
- *"Docker could not attach the NVIDIA GPU"* — enable the WSL 2 backend in Docker Desktop and update
  the NVIDIA driver; `docker run --rm --gpus all nvidia/cuda:12.8.1-base-ubuntu24.04 nvidia-smi`
  should list the GPU.
- RTX 50-series (Blackwell) GPUs need the CUDA 12.8 image this repository builds; older CUDA 12.1
  images fail with "no kernel image is available".

## Phase 2 Scope: Dataset Intelligence

The backend includes a Dataset Intelligence slice for instruction-tuning dataset discovery,
metadata extraction, semantic mapping, validation, and normalization.

```text
FastAPI routes
  -> DatasetService
    -> Dataset providers: Hugging Face implemented, Kaggle/GitHub adapter contracts prepared
    -> SemanticMappingService -> JSON-only LLM mapping client
    -> DatasetValidationService
    -> DatasetConverterService
    -> DatasetRepository -> PostgreSQL caches/history
```

### Implemented Features

- Dataset search through Hugging Face Hub.
- Provider contracts for Kaggle and GitHub dataset sources.
- Metadata extraction without downloading full datasets.
- First-row dataset previews for sample inspection.
- JSON-only semantic mapping through the OpenAI API.
- Mapping cache stored in PostgreSQL.
- Dataset metadata cache stored in PostgreSQL.
- Normalization history stored in PostgreSQL.
- One generic converter to OpenAI `messages` format.
- Validation reports for empty values, missing prompts, missing assistant responses, duplicate rows, long samples, invalid UTF-8, and unsupported schemas.

### Dataset API

Available routes:

- `GET /api/v1/datasets/search?query=...`
- `GET /api/v1/datasets/info/{dataset_id}`
- `GET /api/v1/datasets/preview/{dataset_id}`
- `POST /api/v1/datasets/analyze`
- `POST /api/v1/datasets/normalize`

Example semantic mapping:

```json
{
  "user": ["instruction", "input"],
  "assistant": "output",
  "system": null,
  "context": []
}
```

Normalized output format:

```json
{
  "messages": [
    {
      "role": "user",
      "content": "..."
    },
    {
      "role": "assistant",
      "content": "..."
    }
  ]
}
```

The Hugging Face provider reads metadata and first rows only. It does not download entire
datasets. Semantic mapping calls OpenAI through the provider-agnostic `LLMProvider`
interface and validates that the response is JSON matching the allowed mapping schema.

## Phase 3 Scope: GPU Orchestration

The backend includes a provider-agnostic GPU orchestration layer for lifecycle management.
It does not implement Unsloth training, inference serving, or workload-specific training logic.

```text
FastAPI routes
  -> GPUService
    -> GPURepository -> PostgreSQL lifecycle/events
    -> GPUProvider interface
      -> RunPodProvider
```

### GPU API

Available routes:

- `POST /api/v1/gpu/create`
- `POST /api/v1/gpu/{id}/terminate`
- `GET /api/v1/gpu/{id}`
- `GET /api/v1/gpu`
- `POST /api/v1/gpu/{id}/execute`
- `POST /api/v1/gpu/{id}/upload`
- `GET /api/v1/gpu/{id}/logs`
- `GET /api/v1/gpu/{id}/health`

All GPU routes require JWT authentication. Users can only access their own GPU instances.

The service exposes generic statuses:

- `pending`
- `starting`
- `running`
- `stopping`
- `stopped`
- `failed`
- `unavailable`

RunPod is the first provider implementation. Business logic depends only on the
`GPUProvider` interface, so AWS, Vast.ai, Lambda Labs, and Google Cloud can be added by
implementing the same interface.

Remote upload, command execution, health checks, downloads, and log streaming are routed
through a generic control-agent HTTP contract exposed by the GPU pod image. This phase adds
the orchestration surface only; it does not add a training container or training script.

### GPU Tables

Alembic migration `20260628_0003_create_gpu_orchestration_tables.py` creates:

- `gpu_instances`
- `training_sessions`
- `gpu_events`

## Phase 3B Scope: GPU Runtime Agent

The repository now includes a standalone GPU Runtime Agent under `gpu-agent/`. This FastAPI
service is designed to run inside each GPU pod and expose the control surface used by the
backend `RunPodProvider`.

```text
Backend GPUService
  -> RunPodProvider
    -> GPU pod endpoint
      -> gpu-agent FastAPI app
        -> workspace services
        -> approved training templates
        -> logs/artifacts
```

The agent creates and validates a managed workspace:

- `/workspace/dataset`
- `/workspace/configs`
- `/workspace/templates`
- `/workspace/outputs`
- `/workspace/checkpoints`
- `/workspace/logs`
- `/workspace/artifacts`
- `/workspace/cache`
- `/workspace/temp`

Runtime Agent endpoints:

- `GET /health`
- `POST /upload`
- `PUT /files`
- `GET /files`
- `POST /train`
- `POST /cancel/{training_id}`
- `GET /status/{training_id}`
- `GET /logs/{training_id}`
- `GET /logs`
- `GET /artifacts/{training_id}`
- `POST /download/{training_id}`
- `POST /commands`
- `POST /cleanup`

The backend compatibility endpoints are `/health`, `/files`, `/commands`, and `/logs`.
No backend GPU orchestration business logic is changed for this phase.

Agent environment variables:

- `WORKSPACE_PATH` with default `/workspace`
- `DATASET_PATH` with default `/workspace/dataset`
- `CONFIG_PATH` with default `/workspace/configs`
- `TEMPLATE_PATH` with default `/workspace/templates`
- `OUTPUT_PATH` with default `/workspace/outputs`
- `CHECKPOINT_PATH` with default `/workspace/checkpoints`
- `LOG_PATH` with default `/workspace/logs`
- `ARTIFACT_PATH` with default `/workspace/artifacts`
- `CACHE_PATH` with default `/workspace/cache`
- `TEMP_PATH` with default `/workspace/temp`
- `PORT` with default `8001`
- `MAX_UPLOAD_BYTES` with default `10737418240`

Build the Runtime Agent image:

```powershell
docker build -t llm-fine-tuner-gpu-agent:latest gpu-agent
```

The Docker image installs CUDA-compatible PyTorch, Unsloth, Transformers, TRL, PEFT,
Datasets, Accelerate, Flash Attention, FastAPI, and Uvicorn. Training execution is limited
to approved templates in `gpu-agent/templates`; this phase does not add frontend, inference,
Hugging Face publishing, billing, or full Unsloth training logic.

## Local Development

Copy `.env.example` to `.env`, then install dependencies:

```powershell
npm install
python -m venv apps/api/.venv
apps/api/.venv/Scripts/python -m pip install -e apps/api[dev]
```

Run locally:

```powershell
npm run dev:web
apps/api/.venv/Scripts/python -m uvicorn app.main:app --app-dir apps/api --reload
```

Or run the infrastructure with Docker:

```powershell
docker compose up --build
```

The Docker stack starts local PostgreSQL and Redis for MVP development by default. The local
services are available at `http://localhost:13000` (web), `http://localhost:18000` (API),
`localhost:15432` (PostgreSQL), and `localhost:16379` (Redis). FastAPI's Swagger, ReDoc,
and OpenAPI endpoints are disabled in deployed and local application instances.
